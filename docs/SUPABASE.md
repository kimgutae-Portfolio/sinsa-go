# 기존 Supabase 프로젝트 함께 사용하기

현재 로컬 환경은 `.env`의 기존 Supabase 프로젝트에 연결하고 `STORAGE_BACKEND=supabase`로 실행합니다. **기존 JSON의 통계·등불은 사용자의 선택에 따라 이전하지 않습니다.** `data/visitors.json`, `data/lanterns.json`은 로컬에 그대로 보관하며, 전환 이후의 새 접속·행동·등불부터 DB에 저장합니다. 관리자 페이지는 선택한 저장소의 기록만 표시하므로 과거 파일 기록을 합산하지 않습니다.

## 다른 서비스와의 분리

추가하는 객체는 다음뿐입니다.

| 객체 | 역할 |
|---|---|
| `public.shrine_visitors` | 익명 방문자, 누적 횟수·접속 시간, JST 날짜별 집계 |
| `public.shrine_lanterns` | 등불, 소원·이름, 자리·기간, 소유권 해시 |
| `public.shrine_storage_state` | 저장 버전, 중복 요청 확인, 오래된 서버 쓰기 차단 |
| `public.shrine_save_state(...)` | 데이터셋 단위 트랜잭션 저장 |

기존 서비스의 테이블·정책·Auth·Storage·Realtime 설정과 마이그레이션 이력은 변경하지 않습니다. 테이블 이름 충돌 시 중단합니다. 기존 서비스와는 같은 DB의 컴퓨팅·용량을 공유하므로 자원까지 격리되지는 않습니다.

새 테이블은 RLS를 활성화하고 `PUBLIC`, `anon`, `authenticated` 권한을 모두 회수합니다. 저장 함수도 이 역할에서 호출할 수 없으며, 게임 서버의 서비스 키로만 읽고 씁니다. 기존 서비스의 기본 권한 설정은 바꾸지 않습니다. [Supabase 접근 제어 문서](https://supabase.com/docs/guides/api/securing-your-api).

## 실행 설정

```dotenv
STORAGE_BACKEND=supabase
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SECRET_KEY=서버용_시크릿_키
```

- 기존 `.env`의 `NEXT_PUBLIC_SUPABASE_URL`과 `SUPABASE_SERVICE_ROLE_KEY` 조합도 지원합니다. URL 별칭만 허용하며 공개 키로 서버 저장을 수행하지 않습니다.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`는 이 게임에서 사용하지 않습니다. 프런트엔드는 WebSocket과 인증된 관리자 API로 서버를 거칩니다.
- `.env`는 Git에서 제외합니다. 서비스/시크릿 키를 `VITE_*` 변수로 만들지 마세요. 빌드 결과에 키가 없는지도 검증했습니다.
- 게임 서버는 `.env`를 자동 로드합니다. `.env` 변경 후 서버를 재시작하세요. 운영의 환경 변수가 파일보다 우선합니다.
- `npm run db:check`는 신사 객체만 읽어 연결과 저장 건수를 확인합니다.
- `npm run stats`와 관리자 페이지는 선택한 저장소를 사용합니다. 운영 배포에서 통계 CLI를 쓰려면 개발 도구인 `tsx`도 필요합니다. 관리자 페이지에는 필요하지 않습니다.

처음 다른 프로젝트에 설치할 때는 `npm run db:setup` 또는 SQL Editor에서 `supabase/migrations/202611040001_shrine_storage.sql`만 실행합니다. CLI 로그인/관리 토큰은 최초 스키마 설치용이며, 게임 서버에는 전달하지 않습니다. 설치 스크립트는 기존 테이블의 정의·권한을 전후 비교하고 신사 테이블의 접근 차단을 확인합니다. **기존 서비스에 `supabase db reset`이나 전체 이력의 무분별한 `db push`를 실행하지 마세요.**

## 저장과 장애 처리

- 방문 통계는 메모리에서 집계하고 변경이 있으면 기본 5초마다 DB에 저장합니다. 정상 종료 시에도 저장하며, 강제 종료 시 마지막 저장 이후 기록은 잃을 수 있습니다.
- 등불은 DB 저장 성공 뒤에만 성공 응답과 방 방송을 합니다. 등 내리기·만료 정리도 동일합니다. 현재 등 기록 보관 범위는 기존 로직과 같으며, 영구적인 결제 원장은 아닙니다.
- 데이터셋별 DB 트랜잭션을 사용합니다. 등불 저장 도중 검증이 실패해도 이전 등불이 함께 삭제되지 않습니다. 방/자리, 방/소유권은 DB에서도 중복을 금지합니다.
- 저장 UUID와 버전으로 응답을 잃은 요청을 재확인하고 오래된 서버의 덮어쓰기를 거절합니다. 여러 인스턴스를 운영할 수 있다는 의미는 아닙니다. **게임 서버는 한 프로세스만 실행**하세요.
- DB 장애 때 파일로 조용히 전환하거나 빈 데이터로 시작하지 않습니다. 시작 중 읽기·검증 실패는 시작을 중단하고, 실행 중 통계 저장 실패는 메모리 변경분을 유지해 재시도하며, 등불 저장 실패는 일본어 오류를 반환합니다.
- 부팅 시 API 페이지 제한에 맞춰 모든 기록을 읽고 누락·중복·손상을 검사합니다. 현재 관리자는 서버 메모리의 DB 반영 집계를 조회합니다. 큰 규모에서는 변경된 행만 갱신하고 관리자 검색/집계를 SQL에서 실행하도록 확장해야 합니다.
- DB 전환만으로 로그인·기기 간 복구·멀티 서버 방 공유·결제는 추가되지 않습니다. 익명 브라우저 식별은 그대로입니다. 관리 비밀번호는 계속 서버 환경 변수/비공개 파일에 있습니다.

## 과거 파일

현재 **파일 이전은 하지 않았습니다.** `STORAGE_BACKEND=file`로 시작하면 과거 로컬 기록을 사용할 수 있지만 DB 기록과 자동 병합하지 않습니다. 전환 이후의 새 DB 기록을 파일로 자동 내보내지도 않습니다.

향후 명시적으로 이전할 때만 게임 서버를 멈추고 `npm run db:import`를 실행합니다. 이 명령은 원본을 비공개 백업하고 빈 DB 데이터셋에만 가져오며, 내용이 다른 기존 DB 기록이 있으면 덮어쓰지 않고 중단합니다. 따라서 새 DB 기록이 생긴 뒤에는 별도의 병합 계획이 필요합니다. 이 명령은 서버 시작 때 자동 실행되지 않습니다.

## 검증

- 임시 PostgreSQL 17: RLS·권한, 서비스 역할 저장, 멱등 재시도, 버전 충돌, 잘못된 등불의 트랜잭션 롤백, 기존 서비스 테이블 보존.
- Vitest: API 페이지 제한, 저장소 복구, 통계/등불 연동, 네트워크 응답 유실, 충돌·오류·비밀 키 처리.
- 실제 프로젝트: 추가 전후 기존 테이블 메타데이터 비교와 신사 객체의 접근 차단 확인.
